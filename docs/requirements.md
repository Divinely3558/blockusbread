# BlockUSBRead 需求文档

| 项目 | 内容 |
| --- | --- |
| 文档版本 | v0.1（MVP 需求基线） |
| 日期 | 2026-10-03 |
| 目标硬件架构 | x86_64（amd64），其他架构本期不支持 |
| 交付形态 | 单 Docker 镜像 + docker compose 一键启动 |

## 1. 项目概述

### 1.1 背景与目标

在 Docker 容器中挂载外接 USB 硬盘，**重点支持 BitLocker 加密卷的解密与读取**，并提供一个网页完成「识别磁盘 → 输入凭据解锁 → 挂载浏览 → 安全弹出」的完整流程。

文件浏览能力直接采用开源项目 [filebrowser](https://github.com/filebrowser/filebrowser)，自研部分只做磁盘/加密卷管理，并在视觉与账号上与 filebrowser 保持统一，用户无需感知两个系统。

### 1.2 核心目标

1. 容器启动后自动枚举宿主机上的 USB 块设备及分区；
2. 支持 BitLocker 卷解锁：**用户密码为主，48 位恢复密钥兜底**；
3. 支持多块 USB 硬盘、多个 BitLocker/普通分区同时挂载；
4. 内置 filebrowser，单端口访问，挂载的磁盘在其根目录下按盘聚合浏览；
5. 支持 USB 热插拔实时感知、意外拔出自动清理、网页安全弹出；
6. 默认只读挂载，解锁时可显式选择读写模式。

### 1.3 非目标（本期不做）

- 不做反向挂载到宿主机（不向宿主机传播挂载事件，不暴露 `/media`）；
- 不做多用户与权限分级，只有单一管理员账号（复用 filebrowser 用户体系）；
- 不做 SMB / NFS / WebDAV 等额外共享协议；
- 不做 HTTPS/TLS 终止（假定可信内网，需要时由外部反代提供）；
- 不做 LUKS 等其他加密卷的界面支持（镜像可保留 cryptsetup，但产品上不承诺）；
- 不做空闲超时自动锁定（挂载保持到手动弹出、拔出或容器停止）；
- 不提供非 x86_64 架构镜像。

## 2. 总体架构

### 2.1 容器内组件

```
浏览器
  │  http://host:8000
  ▼
┌─────────────────────────── 容器（privileged）──────────────────────────┐
│                                                                         │
│  FastAPI 主进程 (uvicorn, :8000)                                        │
│  ├── 管理后端 REST API（/api/*）                                        │
│  ├── 管理页静态前端（/，风格对齐 filebrowser）                           │
│  ├── 反向代理 /files/*  ──►  filebrowser 子进程 (:8080, 本机回环)       │
│  ├── 设备扫描器（lsblk / blkid，定时 + 事件触发）                       │
│  ├── uevent 监听线程（NETLINK_KOBJECT_UEVENT，监听 block 子系统）       │
│  └── 挂载编排器（调用 dislocker / mount / ntfs-3g，维护卷状态机）       │
│                                                                         │
│  filebrowser 二进制（官方 linux-amd64 发行版，固定版本+校验和）         │
│    └── 根目录: /mnt/usb   数据库: /app/data/filebrowser.db              │
│                                                                         │
│  系统工具: dislocker · ntfs-3g · exfatprogs · util-linux · udev         │
│                                                                         │
│  /dev/sdX*（来自宿主机 bind）   /mnt/usb/<盘>/<分区>/...（容器内挂载）  │
└─────────────────────────────────────────────────────────────────────────┘
```

### 2.2 目录约定（容器内）

```
/mnt/usb/
└── <disk_id>/                     # disk_id 取盘序列号，缺失时回退为内核设备名
    └── part<N>/
        ├── dislocker-file         # dislocker 解密出的虚拟卷（BitLocker 卷才有）
        └── fs/                    # 实际文件系统挂载点，filebrowser 浏览的就是这里
/app/data/
├── filebrowser.db                 # filebrowser 用户库与配置（账号密码的唯一权威来源）
├── secrets.db                    # 勾选「记住」的卷凭据（加密存储，见 5.3）
└── logs/                          # 应用日志
```

## 3. 功能需求

### FR-1 设备与分区识别

- FR-1.1 通过 `lsblk`（JSON 输出）+ `blkid` 枚举全部块设备，仅展示 USB 外接盘（可通过 `/sys/.../removable` 与设备层级判断，SATA 直插的外接盒也应可见）；
- FR-1.2 每块盘展示：厂商/型号、序列号、设备名（如 `sdb`）、总容量、分区列表；
- FR-1.3 每个分区展示：分区名/标签、容量、文件系统类型、是否 BitLocker 卷（`blkid` 报 `TYPE="BitLocker"`）、卷 UUID、当前状态；
- FR-1.4 BitLocker 卷解锁后，需能识别其**内层文件系统**（以 NTFS 为主）并据此选择挂载驱动；
- FR-1.5 普通（未加密）分区支持类型：**NTFS、exFAT、FAT32、ext4**；识别不到文件系统的分区显示为「不支持」且不可操作。

### FR-2 BitLocker 解锁与挂载

- FR-2.1 解锁凭据二选一：**BitLocker 用户密码**或 **48 位恢复密钥**（前端提供切换，默认密码）；
- FR-2.2 解锁流程：`dislocker` 解密分区生成 `dislocker-file` → 挂载内层文件系统到 `fs/` → 刷新状态；
- FR-2.3 **默认只读**：`dislocker -r` + 文件系统只读挂载（NTFS 走 `ntfs-3g -o ro`）；
- FR-2.4 解锁表单提供「读写模式」勾选项，勾选后以读写方式解锁与挂载，前端需二次确认并提示第三方工具链写入 BitLocker/NTFS 的损坏风险；
- FR-2.5 解锁失败（密码错误、卷损坏等）必须把错误信息明确展示在界面上，清理半成品挂载，不留下垃圾状态；
- FR-2.6 同一卷重复点击解锁时应幂等：已挂载则直接返回当前状态，不重复执行。

### FR-3 普通分区挂载

- FR-3.1 支持对未加密分区直接挂载/卸载，无需凭据；
- FR-3.2 NTFS 一律使用 `ntfs-3g`（读写模式一致的行为）；exFAT 使用 `exfatprogs`；FAT32/ext4 使用内核挂载；
- FR-3.3 普通分区同样默认只读，挂载时可选读写。

### FR-4 多盘多卷

- FR-4.1 支持多块 USB 盘同时在线，每块盘可有多个分区，分别独立解锁/挂载/弹出，互不影响；
- FR-4.2 每个卷的状态、挂载模式（ro/rw）、凭据来源（本次输入/已记住）独立维护。

### FR-5 热插拔与实时刷新

- FR-5.1 监听内核 block 子系统 uevent，设备插入/拔出后自动重新扫描，无需手动刷新；
- FR-5.2 前端通过 SSE（`GET /api/events`）或 WebSocket 接收设备与卷状态变更，页面实时更新；
- FR-5.3 设备拔出时：若卷处于挂载状态，自动按「卸载文件系统 → 断开 dislocker → 删除挂载目录 → 清除内存状态」顺序清理，尽量容忍设备消失导致的卸载报错；
- FR-5.4 保留一个手动「刷新设备列表」入口作为兜底。

### FR-6 安全弹出

- FR-6.1 每个已挂载卷提供「安全弹出」操作：先检查占用（繁忙时给出提示），再卸载文件系统、断开 dislocker，完成后卷回到「未解锁/未挂载」状态；
- FR-6.2 物理盘级别提供「弹出整块硬盘」：该盘所有分区依次卸载清理，成功后界面提示「可以安全拔除」；
- FR-6.3 容器停止时（SIGTERM 优雅退出）卸载全部由本容器建立的挂载并断开 dislocker。

### FR-7 凭据记忆

- FR-7.1 解锁表单提供「记住此卷」勾选项，默认不勾选；
- FR-7.2 **不勾选时**：凭据仅存在于内存并用于当次解锁，拔盘或容器重启后必须重新输入；
- FR-7.3 **勾选时**：凭据加密后写入 `/app/data/secrets.db`，与卷 UUID 绑定，并记录挂载模式（ro/rw）；
- FR-7.4 容器启动或设备插入时，对存在已保存凭据的卷自动完成解锁+挂载，结果（成功/失败）进入设备事件流并通知前端；
- FR-7.5 管理页提供「忘记此卷」入口，立即删除已保存凭据；
- FR-7.6 任何日志、错误回显、接口响应中都不得出现明文密码或恢复密钥。

### FR-8 filebrowser 集成

- FR-8.1 filebrowser 官方 linux-amd64 二进制在镜像构建期下载，**固定版本号并校验 SHA256**；
- FR-8.2 filebrowser 由主应用作为子进程托管（启动、存活探测、异常重启、随容器退出）；
- FR-8.3 filebrowser 仅监听容器内回环地址，对外只暴露 8000 单端口，外部通过 `/files/*` 反向代理访问（配置 filebrowser `baseURL=/files`，正确转发 WebSocket）；
- FR-8.4 filebrowser 单用户模式，根目录固定 `/mnt/usb`：每块解锁的盘是一个子目录，新挂载即时可见、弹出后目录消失；
- FR-8.5 filebrowser 的用户权限范围跟随挂载模式：只读挂载的卷即使在读写账号下也不可写入（由文件系统 ro 保证），不做逐目录权限配置。

### FR-9 认证与账号

- FR-9.1 不自建账号库：**管理页与 filebrowser 使用同一套账号密码**，权威存储为 filebrowser 的用户数据库；
- FR-9.2 首次启动时，用环境变量中的初始账号/密码初始化 filebrowser 管理员用户（已存在初始化记录则不覆盖）；
- FR-9.3 管理页登录由后端校验凭据（调用 filebrowser 登录接口或等价方式校验），通过后建立自己的会话；
- FR-9.4 访问 `/files/*` 时由反向代理共享登录态，实现**一次登录、管理页与 filebrowser 双向通行**（首选 filebrowser 的代理认证/可信头方案，由本机反代注入身份；若不可行则退化为登录态共享跳转）；
- FR-9.5 所有 `/api/*` 管理接口（登录、健康检查除外）必须鉴权；
- FR-9.6 可在管理页修改密码，修改对 filebrowser 同步生效。

## 4. 网页界面需求

### 4.1 页面构成

1. **登录页**（`/`，未登录时）：账号 + 密码，视觉与 filebrowser 登录页保持一致；
2. **磁盘管理页**（登录后首页）：
   - 顶部栏：产品名、当前账号、「打开文件浏览（→ /files）」链接、退出登录；
   - 磁盘列表：以盘为卡片纵向排列（div 垂直布局），盘卡片内列出分区行；
   - 分区行操作按状态切换：
     - BitLocker 未解锁 → 密码/恢复密钥输入、只读勾选（默认勾选只读，即「读写」需主动勾掉/勾选型以最终交互稿为准）、「记住此卷」、【解锁并挂载】；
     - 普通分区未挂载 → 模式选择 +【挂载】；
     - 已挂载 → 状态徽标（只读/读写）、【在 filebrowser 中打开】【安全弹出】【忘记凭据】；
     - 错误 → 黄色提示条展示错误原因（emoji 前缀风格），允许重试；
   - 右上角【刷新设备】；
   - 状态变更由 SSE 实时推送，不轮询；
3. **filebrowser**（`/files/`）：官方原生界面，顶部提供返回管理页的入口（通过 filebrowser 自定义配置/ branding 或外层导航实现）。

### 4.2 视觉要求

- FR-UI.1 管理页整体风格**向 filebrowser 官方界面看齐**：顶栏结构、配色、字体、图标风格、按钮与表格样式统一，避免两个系统割裂感；
- FR-UI.2 浅色为主，跟随 filebrowser 的明暗主题观感；卡片、间距、圆角与其一致；
- FR-UI.3 需兼容移动端窄屏访问（≤480px 时卡片单列、操作区不溢出）；
- FR-UI.4 移动端不展示次要信息（如内核设备名）以避免溢出。

## 5. 非功能需求

### 5.1 部署与运行

- Dockerfile 基线：Debian bookworm slim + Python 3.13（沿用现有 uv 多阶段构建），安装 `dislocker ntfs-3g exfatprogs util-linux udev`；
- docker compose 要求：
  - `privileged: true`（读取块设备、执行 mount 所必需）；
  - bind `/dev`；`/run/udev:ro` 保留（用于 lsblk/blkid 识别型号信息）；
  - **删除现有 compose 中 `/media` 的 rshared 反向挂载配置**；
  - 仅映射 `8000:8000`；
  - 持久化卷仅 `./data:/app/data`；
- 环境变量：

| 变量 | 用途 | 默认 |
| --- | --- | --- |
| `ADMIN_USER` | 首次初始化的管理员账号 | `admin` |
| `ADMIN_PASSWORD` | 首次初始化的管理员密码 | 无，未设置时启动报错并提示 |
| `SECRET_KEY` | 加密「记住的凭据」的主密钥；未设置则禁用记忆功能 | 空（禁用） |
| `FILEBROWSER_VERSION` | 内置 filebrowser 版本 | Dockerfile 固定值 |
| `LOG_LEVEL` | `INFO` / `DEBUG` | `INFO` |
| `TZ` | 时区 | `Asia/Shanghai` |

### 5.2 健康检查

- `GET /health` 无需鉴权，返回主进程存活状态；深度健康项（filebrowser 子进程存活）作为附加字段；
- 保留 Dockerfile 中的 HEALTHCHECK。

### 5.3 安全

- 记住的凭据使用经认证的加密算法（如 Fernet/AES-GCM）加密，密钥由 `SECRET_KEY` 派生；`SECRET_KEY` 不入库不入镜像；
- 凭据内存中短期保存，进程退出即消失；
- 接口默认仅绑定内网，文档明确提示：暴露到公网需自行加 HTTPS 反代与强密码；
- 所有外部命令调用使用参数数组形式（禁止 shell 拼接），凭据通过环境变量/FD 传递，避免出现在进程命令行与 ps 输出中。

### 5.4 可观测性（日志）

- 正常模式（INFO）输出简洁：仅记录关键操作及其结果（谁、对哪个盘/卷、做了什么、成功/失败），例如 `admin 解锁 /dev/sdb1 (卷UUID, ro) 成功`；
- DEBUG 模式输出详细过程：扫描结果、dislocker/mount 命令（凭据脱敏）、uevent 原文、清理过程；
- 任何级别均不得记录明文凭据；
- 日志同时输出 stdout 与 `/app/data/logs/`。

### 5.5 可靠性

- 挂载编排器维护每个卷的状态机：`PRESENT`（已识别）→ `UNLOCKING` → `UNLOCKED` → `MOUNTING` → `MOUNTED(ro|rw)` → `UNMOUNTING` → `PRESENT`；异常进入 `ERROR`；设备拔出进入 `REMOVED` 并清理；
- 容器启动时先做一次全量扫描与状态重建（含已记住凭据卷的自动解锁），再开始服务流量；
- 所有清理路径幂等，重复卸载/删除不得报错中断。

## 6. 接口概览（供详细设计用）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/auth/login` | 登录（凭据经 filebrowser 校验） |
| POST | `/api/auth/logout` | 退出登录 |
| GET | `/api/auth/me` | 当前登录用户 |
| POST | `/api/auth/password` | 修改密码（同步至 filebrowser） |
| GET | `/api/disks` | 当前磁盘/分区树及状态 |
| POST | `/api/volumes/{id}/unlock` | BitLocker 解锁并挂载（凭据、模式、remember） |
| POST | `/api/volumes/{id}/mount` | 普通分区挂载（模式） |
| POST | `/api/volumes/{id}/eject` | 卸载并断开单个卷 |
| POST | `/api/disks/{id}/eject` | 弹出整块盘（其下全部卷） |
| DELETE | `/api/volumes/{id}/credential` | 忘记已保存凭据 |
| GET | `/api/events` | SSE：设备/卷状态实时推送 |
| ANY | `/files/*` | 反向代理到 filebrowser（含 WebSocket） |
| GET | `/health` | 健康检查（免鉴权） |

## 7. 验收标准

1. `docker compose up -d` 单命令启动，浏览器打开 `http://<host>:8000` 出现登录页；
2. 使用初始账号登录后进入磁盘管理页，插入一块 BitLocker USB 硬盘，3 秒内列表自动出现该盘及其 BitLocker 分区；
3. 输入正确 BitLocker 密码（默认只读）可解锁并挂载，点击「打开文件浏览」在 filebrowser 中能看到并读取文件，写入被拒绝；
4. 改用错误密码解锁时，界面明确提示失败且无残留挂载；
5. 使用 48 位恢复密钥同样能完成解锁；
6. 勾选读写模式解锁后，filebrowser 中可上传/修改文件；
7. 勾选「记住此卷」后重启容器，卷自动解锁挂载；不勾选则重启后需重新输入；「忘记此卷」后重启不再自动解锁；
8. 同时插入两块盘（含 BitLocker 与普通 NTFS/exFAT 分区），各卷独立操作互不干扰；
9. 已挂载状态下直接拔盘，界面自动移除该盘且后台无残留挂载点/进程；
10. 「安全弹出」成功后提示可拔除，filebrowser 中对应目录消失；
11. 未登录访问 `/api/disks` 与 `/files/` 均被拦截；登录后两个入口均可用，无需二次登录；
12. 修改密码后重新登录，管理页与 filebrowser 均以新密码为准；
13. 全程日志不出现明文密码；
14. 在 390px 宽手机浏览器上主要操作可正常完成，无横向溢出。

## 8. 待详细设计阶段确认的开放问题

- filebrowser 代理认证在其当前固定版本上的具体接法（proxy auth 头 vs 登录态桥接），以可行性实测结果为准；
- 硬盘序列号缺失/重复时 `disk_id` 的最终回退规则；
- 「busy 设备无法弹出」时是否提供强制卸载选项（MVP 倾向只提示不强制）。
